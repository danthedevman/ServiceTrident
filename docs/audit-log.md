# Audit log

Admins open **Settings → Audit log** to review activity in their workspace. Search all columns or one column, filter by UTC date, sort using column headings, and select 10, 25, or 50 rows per page. CSV exports use the same server filters. Timestamps display in the viewer’s saved timezone and date/time format; date filters and CSV keep their documented machine/UTC format. Open Record opens a read-only entry with the same admin/workspace restrictions as the list. Entries cannot be edited or deleted through the application. Automated activity is labeled System, including legacy branded actor labels for display.

Every API response now produces an audit entry, including authentication, record changes, list reads and polling, individual reads, downloads, exports, external record creation, OAuth token requests, failures, and audit-table access. Verified users and service accounts retain their identity and workspace attribution. Successful public-status requests use the verified public page’s workspace. Requests without a verified workspace are stored with no workspace and cannot appear in another tenant’s audit table. Health checks and early rejected requests therefore remain deployment-level entries. Invitation acceptance and worker-created/resolved incidents are also recorded. Scheduled monitor results remain in monitor check history; the API request used to read that history is audited. Demo-data operations and cascading deletes retain their initiating audit operation.

No request bodies, field values, passwords, integration secrets, session/invitation tokens, query strings, comment text, or attachment contents are copied into audit history. Submitted fields identify what was requested, not a verified before/after diff. Actor names and record IDs are retained after a record is deleted. Restrict access to backups accordingly.

History starts when this feature is deployed; older activity cannot be reconstructed. MongoDB and PostgreSQL both store audit entries in `auditEvents`, with workspace/time and record indexes. PostgreSQL migration 2 adds the collection table without changing existing records. Entries have no automatic expiration; include them in database backups and capacity planning.

This is an application activity log, not a tamper-proof compliance ledger. Business changes and audit inserts are separate database writes, so a process crash between them can leave a gap. For ordinary JSON/write responses, the API waits for the audit insert before ending the response; if insertion fails it reports an error when headers permit and asks the user to refresh before retrying. Already-streaming downloads cannot be recalled on an audit failure. Database administrators can modify stored entries outside the app.

RCA Form Builder configuration reads and saves, record creates, updates, archive/restore status changes, reads, list polling, and exports use the same API audit middleware. Automatic alert-group membership updates emit worker audit entries with field names only; analysis contents and check diagnostics are excluded from audit metadata.

Record actions → Export CSV / Export PDF re-read the saved record through its normal authorized endpoint. Audit entries record an export request, its format and API outcome; collection-backed targets must appear in the authorized response before their identifier is attached. No exported text or query strings are logged. The PDF is rendered locally in the browser, so the API entry confirms the read outcome rather than successful file generation.
